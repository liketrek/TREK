# TREK v5.2.0 upgrade assessment

The goal is to bring v5.2.0 onto a branch from dev while preserving existing trips and fork behavior. Use the official release as the implementation baseline for the database, Costs, and PDF. Port the fork behavior into those modules. A direct merge needs manual decisions even for files Git merges cleanly.

## Database compatibility

**Existing SQLite installs.** The fork created `day_assignments.stay_minutes` with a 1,440-minute maximum. Official migration 46420 skips an existing column. Upstream accepts up to 10,080 minutes. An upgraded fork can therefore accept a request at validation and reject it at the database. Reconcile the constraint in a new migration, preserve saved values, and exercise null, zero, one day, and seven days on an upgraded database.

**PostgreSQL.** Upstream initializes a fresh database from a schema snapshot and records official migrations through 46440. Three historical fork migrations use SQLite connection methods. Their full names are absent from the official snapshot manifest. Combining the catalogs would leave these SQLite migrations pending on PostgreSQL. The fork needs equivalent tables, columns, and migration receipts on PostgreSQL, plus a verified copy of fork data during SQLite-to-PostgreSQL moves. Include the historical Web Push table in that verification. Preserve all published SQLite migration identities, including distinct names with the same numeric prefix.

Keep the SQLite CLI guard that prevents legacy databases from bypassing the fork migration runner. Keep the current SQLite deployment configuration and its volume backup hooks. A switch to an external PostgreSQL server would require a separate database backup.

Before calling a candidate ready, compare a clean upstream build with the candidate, exercise fresh installs on both engines, upgrade the supported legacy and current fork SQLite histories, and repeat startup. On a disposable copy, check the database move, audit receipts, guest transfers, encrypted records, saved FX, and visit timing. Then test desktop and mobile Costs, PDF, sharing permissions, and the fork deployment build. The release deploys from the fork’s `release` branch.

## How to reproduce the comparison

Use the two full commit IDs in the table for repeatable results. The first command returns their common ancestor. The second prints a proposed tree followed by conflicting paths and exits with status 1 for conflicts. It leaves branches and the checkout untouched.

```sh
git merge-base e57b3b96c009bed5834d037fd2932cf49b6faeac 8809654a43fe718605c03530bd78367f431719ea
git merge-tree --write-tree --name-only e57b3b96c009bed5834d037fd2932cf49b6faeac 8809654a43fe718605c03530bd78367f431719ea
```

This assessment covers the published dev history. The active guest-identity checkout also contains uncommitted work. The feature branch was created in a separate worktree to preserve it. Results above come from release metadata, Git history, source inspection, and a simulated merge. Runtime compatibility still needs verification.
